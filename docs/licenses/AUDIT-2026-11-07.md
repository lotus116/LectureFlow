## 结论与范围

用户选择“他人发布修改版时也开源”，据此为项目自有代码落实 **GPL-3.0-only**。
使用明确的第 3 版，不自动授权尚未知晓的未来 GPL 版本。采用 GPL 不限制商业
使用，也不要求纯自用修改公开；涉及分发时按完整许可证履行义务。

**这次完成了源码许可声明、第三方证据整理和发布前检查设施，尚未完成全部
二进制／素材再分发许可闭环。** 既有 v0.6.5 包未被替换，也不能因新增 LICENSE
而倒推其内已经包含所有许可、对应源码和素材授权。

核查主线起点 `985fcb6`、公开 v0.6.5，以及 Mac 当前安装环境和 Windows 已公开
ZIP 的目录／实际文件。主线作者名称 lotus116、cclear116 对应同一作者身份，
发现 Cursor 协作署名；未发现第三方 PR 合并。第三方 [PR #6](https://github.com/lotus116/LectureFlow/pull/6)
仍开放，不能用本次许可决定替作者授权。Git 作者记录是来源线索，不是全面
权属证明；未来贡献规则见 [CONTRIBUTING](../../CONTRIBUTING.md)。

## FFmpeg：封装许可证不等于实际二进制许可证

[imageio-ffmpeg 0.6.0](https://github.com/imageio/imageio-ffmpeg/tree/v0.6.0)
Python 封装为 BSD-2-Clause，但它打包的 FFmpeg 各平台构建不同。

- **Mac arm64**：本机实际 `ffmpeg-macos-aarch64-v7.1` 的 `-L` 声明
  GPL-2.0-or-later；配置含 `--enable-gpl`、x264、x265 等。以其允许的 GPLv3
  兼容版本交付是可能的，但需独立履行对应源码／声明义务。公开 v0.6.5 的
  实际二进制也已提取并复核相同许可／配置，SHA-256 为
  `6d175a4743ca50256e89a8cdd731100f9cee33bd79aeea46894d209410dc6617`。
- **Windows x64 v0.6.5 公开 ZIP**：实际
  `ffmpeg-win-x86_64-v7.1.exe` 是 `7.1-essentials_build-www.gyan.dev`，配置含
  `--enable-gpl --enable-version3 --enable-static`，内嵌许可为 GPLv3-or-later。
  SHA-256 为 `2ce797a0f88d7f067180338fb227f7b1928ea727bd9a4d7a1d022f7c52af71a3`。
  与 [Gyan 7.1 官方 ZIP](https://github.com/GyanD/codexffmpeg/releases/tag/7.1)
  中 exe 摘要相同。原 Gyan 包含 GPLv3 LICENSE 和 README，LectureFlow 包内
  没有保留这两份，仅有 imageio 封装许可。
- Gyan README 指向 FFmpeg commit `b08d7969c5`，列出部分第三方库版本，但未
  覆盖全部静态依赖和构建材料。一个 FFmpeg 源码链接、版本号或 GPL 文本不足
  以代表该完整构建的对应源码。现阶段尚未取得两平台完整的对应源码材料。

## Windows 冻结包与原生库

已读取公开 Windows ZIP 中 1,560 个条目，并只读解析 EXE 中 PYZ：pystray 的
13 个模块确实被封装进去，而外层没有其源码、dist-info 或 GPL/LGPL 许可。
[pystray 0.19.5](https://github.com/moses-palmer/pystray/tree/v0.19.5)
源头是 LGPL-3.0-or-later，与 GPLv3 项目可兼容，但必须提供适用的声明、源码
和修改／重建方式。默认 PyInstaller 先查 PYZ，向目录随便放一份 `.py` 不能
保证覆盖内部模块；本次专用 hook 旨在修复这种交付方式，不能替代 Windows 验收。

已发布 ZIP 中能找到 numpy、PDFium、sherpa-onnx、TkDND、WinRT、imageio 以及
模型／llama 的部分许可；未发现 pystray、Python PSF、Pillow、psutil、pypdf、
olefile、six、sounddevice/PortAudio、OpenSSL 的单独完整声明。新收集器会补
安装环境中存在的声明，并列出找不到文件的包；还需人工核对最终 native 库。

当前 `--collect-binaries _sounddevice_data` 将多个架构、ASIO 版 PortAudio
及 macOS dylib 一并收入 Windows 包。ASIO SDK 的独立条款及构建来源尚待核查，
不能因为 PortAudio 顶层是 MIT 就跳过。缩减不使用的库或调整音频后端前先
验证实际需求与行为，不在本次静默改变用户采集能力。

[llama.cpp b9000](https://github.com/ggml-org/llama.cpp/blob/b9000/LICENSE)
MIT 和 [sherpa-onnx 2.0.1](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.1/LICENSE)
Apache-2.0 的顶层许可已核实；这不等于覆盖全部 DLL。
[PyInstaller](https://pyinstaller.org/en/stable/license.html) 的分发例外需保留，
不能把它简化为“应用必须 GPLv2”。PDFium、TkDND、PortAudio 也应按实际随包
文件保留各自声明。

## 依赖版本与 regex 待澄清点

Mac 打包从现有 `.venv` 复制多数依赖，不一定仅包含新鲜解析的运行依赖；Windows
setup 混合固定与未固定的依赖，Pillow、WinRT 等没有被 `uv.lock` 完整锁住。
所以每次需要保存实际安装／最终二进制清单，不能把 lockfile 当成两端完整 SBOM。

本机元数据中 tqdm 4.70.1 为 MPL-2.0 AND MIT，regex 2026.9.29 为
Apache-2.0 AND CNRI-Python。regex 原文称继承 CPython 2.6/3.1 的 re 代码并引用
CNRI Python 1.6；CPython 发布许可又包含 GPL-compatible 说明。这是待澄清的
继承条款问题，**没有认定它已经不兼容**，也不擅自改写上游 SPDX 字段。

直接相关讨论：[regex #622](https://github.com/mrabarnett/mrab-regex/issues/622)、
[#362](https://github.com/mrabarnett/mrab-regex/issues/362)、
[#579](https://github.com/mrabarnett/mrab-regex/issues/579)、
[CPython #100079](https://github.com/python/cpython/issues/100079)、
[CPython 3.1 LICENSE](https://github.com/python/cpython/blob/v3.1/LICENSE)。
发布前需结合原文、来源和适用条款复核，而不是把一个元数据标签当最终结论。
